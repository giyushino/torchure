# First Real Multi-GPU Run — 8x A6000, DDP

First end-to-end pretraining run on the 8x RTX A6000 box: 16,000 steps,
2.10B tokens, 6.7h wall clock, finished clean. This note records the run,
the infra built to support it (wandb, checkpoint completion markers, eval
entrypoints), and the issues found along the way.

Run: `climbmix_long_test_run_ddp_a6000` | wandb `grauoali` |
2026-07-30 22:39 -> 2026-07-31 05:21
Config: `configs/qwen3_dense_climbmix_ddp_a6000.json` (was
`qwen3_dense_climbmix_ddp.json` at launch time; renamed afterwards when the
h100 variant was added)

## Result

| | |
|---|---|
| steps | 16,000 (completed, LR fully decayed) |
| tokens | 2.10B (3.65 tok/param) |
| wall clock | 6.7 h |
| final train loss | 2.836 (last step) / **2.724** (mean over last 200) |
| held-out ppl | **~20** (shard 60; see caveat below) |
| throughput | ~88k tok/s, 1.506 s/step |
| MFU | ~24.5% (6ND approximation, excludes attention FLOPs) |
| peak cuda mem | 27.58 GiB |
| checkpoints | 4 x 6.5 GB = 26 GB |

Model: qwen3 dense, 28 layers, emb 1024, head_dim 128, 16 heads / 8 kv
heads, vocab 151,936 -> **574.0M params** (418.4M non-embedding; lm_head is
tied to token_emb). seq_len 4096, global batch 32 (2 microbatches/step at
dp=8, micro_batch 2), AdamW lr 3e-4, WSD with 160 warmup steps and decay
from step 14400.

### vs the scaling law

Chinchilla (`L = E + A/N^a + B/D^b`, Hoffmann et al. 2022) predicts **3.13**
at 574M params / 2.10B tokens. We got **2.836** — about 0.3 better.

The law also tracked the run *during* training: at step 252 it predicted
5.34 against ~5.1 observed. Beating it at the end is plausibly ClimbMix
being a filtered/curated mix rather than raw web text, plus the tokenizer
difference (the law was fit on MassiveText with a 32k vocab; we use Qwen3's
152k). Either way this is the strongest single piece of evidence that the
training stack is numerically correct — a broken mask, wrong RoPE, or
mis-shifted label would show up as sitting *above* the curve, not below.

## Throughput

| config | tok/s | s/step | notes |
|--------|-------|--------|-------|
| gbs 16 (1 microbatch/step) | ~78k | 0.84 | earlier 100-step shakedown |
| **gbs 32 (2 microbatches/step)** | **~88k** | **1.506** | this run |

Doubling the global batch bought ~13% throughput: the DDP bucket all-reduce
is amortized over two backwards instead of one. Note that s/step doubled —
tokens/sec is the invariant, not step time.

Checkpointing cost `4.64s` for 6.5 GB (`@debug_time` on `Trainer.checkpoint`),
4 times over the run — under 0.01% of wall clock. `save_steps` can safely
drop to 1000 next time; 4000 was chosen conservatively and left ~1.9h of
crash exposure for no real benefit.

## GPU 7 is thermally throttled

**The single biggest throughput loss on this box.** Confirmed via
`nvidia-smi -q`: `SW Thermal Slowdown: Active` on GPU 7 and nothing else.

| | GPU 7 | GPUs 0-6 |
|---|---|---|
| temp | **90-92 C** | 65-75 C |
| fan | **100%** | 37-48% |
| SM clock | **1410-1455 MHz** | 1620-1935 MHz |
| power | 214 W | 222-239 W |

Card thresholds: max operating 93 C, HW slowdown 95 C, shutdown 98 C. GPU 7
sits 1 C under max operating, so the driver holds it down — the card is not
in danger, the throttling *is* the protection, but it costs speed.

DDP is synchronous: every step ends in an all-reduce that waits on the
slowest rank, so GPU 7's clock sets the pace for all eight. A healthy GPU 7
is plausibly worth 15-25% (~100k+ tok/s, which would have made this a ~5.5h
run instead of 6.7h).

Fan is pinned at 100% and *responding*, so it isn't a dead fan — the cooling
path just isn't moving heat. On a blower-style A6000 in a dense chassis
that's usually dust in the intake/fins or pumped-out thermal paste. Same
card in both runs, so it's the physical card or slot, not the workload.
**Check the intake for dust first.** Watch GPU 6 too — caught it at 1500 MHz
in one sample at 74 C, which may be the same problem one slot over.

Also note the earlier A40-era numbers in `CHANGES.md` come from 20-step
benchmark runs that finish before the box heat-soaks. Those are cold-GPU
numbers and will always look better than a real run.

## Infra built for this run

### wandb integration (`trainer.py`)

- `_setup_wandb()` — rank 0 only (every rank calling `init` would open
  `world_size` duplicate runs), gated on `config["wandb"]["enabled"]`,
  skipped in benchmark mode. Passes the full config as run hyperparameters
  so runs can be diffed in the UI instead of by digging up json.
- `_log_metrics()` — loss, grad_norm, lr, cumulative tokens, tps, step_time,
  peak mem. Logged at `step + 1` to match checkpoint numbering: wandb DROPS
  any log at a step <= the last recorded, so a resumed run whose numbering
  disagrees with the pre-crash run loses steps silently.
- **wandb run id round-trips through `trainer.pt`**, so a resume reattaches
  to the same run (`resume="must"`) instead of splitting one loss curve
  across a new run per restart. Read back with `.get()` so pre-wandb
  checkpoints still load.
- `wandb_run.finish()` in a `finally` — a crash marks the run crashed rather
  than leaving it "running" until wandb times it out.
- `benchmark` flag on `Trainer.__init__`, passed as `args.steps is not None`
  from `train.py`: benchmark runs are a tps measurement, not an experiment,
  and shouldn't pollute the project.

wandb's automatic system metrics turned out to be the diagnostic that found
the GPU 7 problem — per-GPU temp, fan, SM clock and power are all in the run
stream without any extra instrumentation.

### Checkpoint completion markers (`checkpointer.py`)

A step dir exists from the moment its first file lands, so the dir alone
proves nothing — a crash mid-checkpoint used to leave a half-written dir
that `latest()` would happily return, and resume would die on the missing
`optimizer.pt`.

Now `Trainer.checkpoint` writes an empty `.complete` into the step dir as
the last action, **after the barrier** (the dataloader files are per-dp-rank,
so rank 0 finishing its own four saves does not mean the step is done), and
`latest()`/`valid_step()` only consider marked steps. Any crash before the
marker leaves an ignored partial dir instead of poisoning the next resume.

This makes atomic renames unnecessary: every step gets a fresh directory and
the marker is written last, so "crash anywhere" and "torn `torch.save`" land
on the same outcome. The one residual case is *rewriting* a step that was
already complete (resume from an earlier step, train forward past it) —
handled by clearing the marker first, or by never rewriting a step.

`tests/checkpointer.py` gained `check_completion_marker()` covering: all
files written but unmarked (not resumable), torn write at step 20 falling
back to 10, explicit `valid_step` on a torn step refused, idempotent
re-marking, never-written steps, non-numeric dirs. Mutation-tested — both
bugs below fail the suite when reintroduced.

### Eval entrypoints (`torchure/eval/`)

- `loader.py` — rebuilds the model from the checkpoint alone. `trainer.pt`
  carries the config the run was launched with, so eval needs no json, no
  mesh, no process group.
- `perplexity.py` — held-out ppl using the same next-token shift as
  `ARObjective`. Accumulates summed NLL and a token count then divides once
  (a mean of per-batch means would weight a short final batch equally).
- `generate.py` — sampling REPL with temperature/top-k/top-p, streams
  tokens, ~32 tok/s. No KV cache: the model doesn't implement one, so each
  token re-runs the full prefix (quadratic). Fine at this scale.

## Bugs found

1. **Timestamped `run_name` silently broke resume.** `checkpointer_path` was
   built from `f"{run_name}_{datetime.now()}"`, so every launch got a fresh
   empty directory and `resume="auto"` could never find anything — it would
   silently restart from step 0. Worse under DDP: each rank computes its own
   `datetime.now()` and gets its own directory. Fixed by splitting the two
   names — checkpoint dir keyed on `config["run_name"]` alone (stable, so a
   relaunch lands in the same place), timestamp only on the wandb display
   name where per-launch is what you want.
2. **`mark_complete` opened the marker for reading.** `open(path)` defaults
   to mode `"r"`, so it raised `FileNotFoundError` on a file that by
   definition doesn't exist yet — would have killed the run at the first
   save step. Needs `open(path, "w")`.
3. **`valid_step` bypassed the completeness check.** `latest()` was updated
   to filter on the marker but `valid_step()` kept the old comprehension, so
   `resume="auto"` was protected while explicit `resume=<int>` would still
   load a torn checkpoint — the path where a corrupt load is *most*
   confusing, since you named that step deliberately.

## Held-out perplexity

**Shards are not interchangeable.** Measured on the step-16000 checkpoint:

| shard | loss | ppl |
|-------|------|-----|
| 0 | 2.92 | 18.5 |
| 25 | 2.99 | 19.8 |
| 60 | 3.04 | 20.8 |
| **99** | **3.36** | **28.8** |

`perplexity.py` originally defaulted to the last shard and reported 30.9,
which looked like a large train/held-out gap. It's mostly shard 99 being a
harder slice — consistent with per-batch training loss swinging between 1.77
and 3.98. Default is now shard 60. **Compare runs on the same `--shard` or
not at all.**

For reference `exp(2.724) = 15.24`, so the real train -> held-out gap is
~0.3 nats, which is small and expected for single-pass pretraining with no
repetition.

Perplexity is **not comparable across tokenizers** — a 152k vocab packs more
text per token than a 32k one. Bits-per-byte (normalize NLL by UTF-8 bytes
instead of tokens) is the comparable metric and is not yet implemented.

## Generation samples

Base model, no instruct tuning, no chat template — it completes text rather
than answering questions.

> **The capital of France is** Paris and the capital of the Netherlands is
> Amsterdam. The Netherlands is one of the largest cities in the world with
> 3.3 million residents and 211,000 employees.

Paris is right; the Netherlands is then confused for a city. Grammar and
discourse structure are solid, facts and reasoning are not — about what 2.1B
tokens buys.

`Q: What is 2 + 2? A:` degenerates into `2 is the complement of 2` on
repeat. `def fibonacci(n):` drifts into prose, suggesting ClimbMix has
little code. Prompt it like the pretraining corpus, not like a chatbot.

## Known issues / next

- **GPU 7 thermal throttling** — physical fix, gates every run on this box.
- **100 shards % dp 8 != 0.** `split_dataset_by_node` only assigns shards
  cleanly when `num_shards % world_size == 0`; otherwise every rank streams
  the *entire* dataset and keeps 1 example in N. At dp=8 that's 8x the
  network egress and tokenization CPU, sustained for the whole run. Didn't
  bound throughput here (GPU-bound), but it's pure waste. dp=4 or dp=5
  divides 100 evenly.
- **The final checkpoint only saves if `total_steps % save_steps == 0`.**
  There is no unconditional save after the loop. With WSD the last 10% is
  the LR decay, so a non-divisible pair silently discards the fully-decayed
  weights — the checkpoint you actually want. Worth an unconditional
  end-of-run save, guarded against double-writing.
- **No checkpoint retention policy.** `Checkpointer` never deletes. 26 GB
  here, but ~560 GB for a Chinchilla-scale run at `save_steps=1000`.
- **No KV cache** — generation is quadratic in length.
- **No standard benchmarks.** `lm-evaluation-harness` via an
  `lm_eval.api.model.LM` subclass would be the route; at 574M / 2.1B tokens
  expect most tasks at or near chance (HellaSwag 25%, PIQA 50%), with
  LAMBADA/PIQA/HellaSwag the first to move.
- Chinchilla-optimal for this model is 11.5B tokens (~87,600 steps, ~41h at
  this throughput), predicted loss 2.74.
