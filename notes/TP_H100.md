# tensor parallel on 4×H100 NVL — throughput, sp layout, and comm overlap

box: 4× H100 NVL (93.08 GiB usable HBM each), nvlink pairs 0-1 and 2-3 (NV12),
pcie between the pairs. `seq_len=4096`, ClimbMix, per-block
`compile(mode="default")`, bf16 autocast, fused AdamW, fused linear CE.
runs 2026-11-12, main at 0adbf01 plus the overlap / sp_dim work below (since
committed in a3c920c). config defaults live in `torchure/config.py`.

three questions: what does tp cost against plain fsdp on one node, does the
sequence-parallel layout matter, and does hiding tp's collectives behind
compute (the overlap modes) pay. the short version: **on one node at ≤4B, fsdp
over all four gpus beats every tp layout (−12% at 0.6B, −7% at 4B for the best
one). sharding sp along the batch instead of the sequence is a free +6-7%. the
overlap modes lose 1-5% and cost ~5 GiB here; nvlink leaves little comm to
hide.**

## method

`train.py --steps 50` on generated configs, tps read off the step-50 log line
(the mean over steps 41-50, well past compile warmup; steps 31-40 agree within
1% everywhere). one run per config, run back to back, NOT interleaved A/B,
so the thermal drift noted in ROADMAP's correctness debt applies; treat
differences under ~2% as noise. global batch fixed per model (32 seqs at 0.6B,
16 at 4B) with micro batch chosen for no grad accumulation where it fits, so
every layout trains the same tokens per step and per gpu.

MFU uses the README formula, `6N + 12·L·H·head_dim·seq` flops/token
(N = 574M / 4.02B → 6.26 / 31.4 GFLOP/token), against 835 TFLOP/s dense bf16
per gpu.

## findings

**tp doesn't buy capacity or speed on one node at these sizes.** fsdp already
shards params/grads/optimizer state over all 4 gpus; fsdp 2×tp2 shards them
over the same 4 (2 × 2), so model state per gpu is identical. tp's extra is
activations: one sequence is split across the tp group. at equal tokens per
gpu that saves nothing (4B: fsdp4 mb4 82.1 GiB vs fsdp 2×tp2 mb8 86.4 GiB, tp
slightly *worse*: each rank still keeps the gathered region inputs for
backward). tp starts to matter only once one sequence at mb 1 doesn't fit
(the 14B ceiling in FSDP2_H100.md is exactly that), for long context, or
multi-node when global batch caps the dp degree.

**tp 4 crosses pcie.** with tp 4 every collective spans the pcie hop between
the nvlink pairs: 83k vs 162k for 2×2 at 0.6B. tp groups must stay inside an
nvlink domain; the mesh's tp-innermost order does that for tp 2 here.

**sp along the sequence costs layout copies.** with micro batch > 1, an
all_gather / reduce_scatter along dim 1 goes through `movedim(...).contiguous()`
and hands the linear a strided view, so every region entry and exit copies.
that's why "sp off" (172k) beat sp on seq (162k) at 0.6B. `tp.sp_dim: "batch"`
shards dim 0 instead: chunks are contiguous, no copies, and norms/residuals
are token-wise so the split dim doesn't matter to them. +7% at 0.6B (fsdp
and ddp), +6% at 4B, no memory change. needs `micro_batch % tp == 0`;
otherwise keep "seq".

**overlap doesn't pay on nvlink.** rough budget at 0.6B mb16: one region
collective moves ~134 MB per rank, ~0.5 ms on NV12; 8 per block × 28 blocks
≈ 0.1 s of an ~0.8 s step, so ~12% is the most there is to hide. against
that the fused ops add (not profiled; this is the reading, not a trace):
- graph breaks: column/row linears run outside the compiled block, so q_norm,
  rope, silu·up land in small separate graphs;
- copies of the incoming grads into rows layout in backward (and of
  everything under sp_dim seq);
- an fp32 dX buffer (the reduce-scatter dtype) held while the weight grads
  run: the ~5 GiB, which is what pushes 4B mb8 over;
- collective_matmul additionally splits each GEMM into tp smaller ones and
  runs nccl p2p kernels that compete for SMs.
expect it to help with slower links (tp over pcie or across nodes) or much
wider matmuls; on this box leave it off.

## the overlap implementation (`parallelism/tp_overlap.py`)

config `tp.overlap`: "none" (default) | "backward" | "collective_matmul";
needs sequence parallel. each region's entry all_gather + all of its column
linears become one autograd op, and its row linear + exit reduce_scatter
another. the region's pre hook runs every column linear at once and parks the
outputs; the column linears' forward just returns them. weight grads come
back as ordinary autograd grads, so ddp/fsdp grad hooks fire unchanged.

- backward: launch the reduce_scatter of dX async, compute dW_i = dY_iᵀ X
  while it flies, then wait.
- collective_matmul: every collective becomes tp ring steps over row chunks
  (`ring_send_recv`, now async with a caller-owned recv buffer), each overlapped
  with the matmul on the chunk already held. the in-flight send buffer is held
  until its wait so the allocator can't hand its memory to the next matmul.
- the pre hook and row forward are `torch.compiler.disable`: traced, the
  per-region lookup guarded on the module and recompiled per region until
  dynamo hit `recompile_limit` (8) and fell back to eager. the first overlap
  sweep ran like that; the numbers above are the rerun.

## open problems

- **collective_matmul hangs at 4B under fsdp 2×tp2 with sp_dim seq.** twice,
  no error, killed by the 15 min timeout; 0.6B and ddp×tp were fine.
  unconfirmed guess: the tp ring's p2p ops and fsdp's prefetch all_gathers
  (different communicators, different streams) are enqueued in different
  orders on different ranks and deadlock. not debugged.
- **the overlap ops are only correctness-tested in fp32 on cpu/gloo**
  (`tests/tensor_parallel.py`, 7 scenarios: both modes, both sp dims, ring 2
  and 4, ddp and fsdp incl. padded shards). bf16 casting and real concurrency
  are only exercised by the gpu runs above (losses match baseline), with no
  test enforcing it.
- not run: hsdp × tp, multi-node tp, a profiler trace of the overlap modes,
  and the experiment that would show tp's real value here: largest model
  that fits at mb 1 for fsdp4 vs fsdp 2×tp2, with and without activation
  checkpointing.
